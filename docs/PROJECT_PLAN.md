# Genisource ERP 项目规划

> 版本：v0.1 | 日期：2026-10-27
> 状态：所有关键决策已确认，M0 已实施

---

## 0. 一页纸摘要

| 维度 | 结论 |
|---|---|
| 一句话定位 | 面向国内中小制造业的开源 ERP，以 MRP 运算为内核，与 Genisource MES 组成「计划层 + 执行层」套件。 |
| 目标客户 | 50–500 人、离散制造（电子装配、机加工、注塑、五金、小家电），1–3 个工厂。 |
| 核心价值 | BOM 算得准、MRP 算得快、采购销售库存财务一本账，并能与车间执行打通。 |
| 开源许可 | **Apache-2.0**，与 MES 统一；商业化走 Open Core（增值模块 + 服务）。 |
| 技术栈 | Java 21 + Spring Boot 4.1 + Spring Data JPA + Flyway + PostgreSQL 17；React 19 + TypeScript + Vite + TanStack Query + Zustand。 |
| 部署形态 | 多租户架构（行级隔离），一套代码同时支持私有化单租户与 SaaS 多租户。 |
| 与 MES 关系 | 独立仓库、独立部署，通过 REST API 集成。 |
| 最大风险 | 范围蔓延。必须靠「不做清单」和纵向切片保命。 |

## 1. 差异化

| 维度 | Genisource ERP | jshERP | T3rik | Metasfresh | Odoo | ERPNext |
|---|---|---|---|---|---|---|
| 核心能力 | MRP + 进销存 + 财务 + MES 集成 | 进销存 + 财务 | MES 为主 | 制造完整 | 全功能 | 全功能 |

## 2. 明确不做（写进 README，挡住需求）

- ❌ 全行业通用 ERP——只做离散制造，流程行业不在范围内
- ❌ 完整 APS 有限产能排程——核心只做 MRP 净需求，APS 属企业版
- ❌ WMS 立库调度、AGV 调度——只做仓库级库存
- ❌ 集团级合并报表、多会计准则——核心只做单组织简化财务
- ❌ 低代码表单引擎、可视化流程设计器——审批用 Flowable 内置 BPMN
- ❌ 自研数据库、消息中间件、工作流引擎
- ❌ 移动端 App（M5 之后评估，先用响应式 Web）

## 3. Open Core 边界

### 开源核心（Apache-2.0，永久免费）

平台基座（多租户 / RBAC / 审计 / 工作流 / 报表）、主数据（物料 / 客户 / 供应商 / BOM / 工艺 / 工作中心）、库存、采购到付款、销售到收款、MRP 运算、生产订单（计划层）、简化财务（凭证 / 总账 / 三大报表）、MES 集成适配器。

### 企业版增值（商业许可，`backend/ent-*`）

成本核算、APS 高级排产、QMS 质量管理、EAM 设备资产、多组织合并、高级财务（多币种 / 金税 / 预算）、移动端 PDA、BI 驾驶舱、SLA 支持。

**加载机制**：增值模块是独立 Maven 模块，通过 Spring Boot auto-configuration + `@ConditionalOnProperty` 按 License 加载；核心模块**禁止**依赖 `ent-*`，由 ArchUnit 守护（见 ADR-0004）。

## 4. 版本路线图

| 里程碑 | 周期 | 交付物 | 验收标准 |
|---|---|---|---|
| **M0 脚手架** ✅ | 第 1–2 周 | 多模块骨架、多租户基座、JWT + RBAC、Flyway 基线、部署编排、CI、文档 | `docker compose up` 起得来；登录 / 刷新 / 权限跑通；审计表就位 |
| **M1 主数据** ✅ | 第 3–6 周 | 物料（采购/销售/财务属性）、客户、供应商、BOM 多级/版本/替代料、工艺路线、工作中心 | 物料 CSV 导入导出；BOM 多级展开（递归 CTE）；与 MES `md_item` 可映射 |
| **M2 库存** ✅ | 第 7–10 周 | 仓库/库位/批次/序列号、库存账、出入库单据、盘点、FIFO/移动加权平均 | 出入库闭环；库存账实时；批次追溯可查 |
| **M3 购销** | 第 11–16 周 | 请购 → PO → 收料质检 → 入库 → 应付；报价 → SO → 发货 → 出库 → 应收；Flowable 审批 | 端到端单据流转；自动生成应收应付凭证；与库存联动 |
| **M4 MRP + 生产订单** | 第 17–22 周 | MRP 运算（净需求）、计划工单、计划采购单、生产订单、领料、完工入库 | SO → BOM 展开 → 库存抵扣 → 计划单；生产订单可下达 MES |
| **M5 财务 + 集成 + v1.0** | 第 23–26 周 | 科目/凭证/总账/三大报表、MES 双向集成、硬化、离线包 | 业务单据自动生成凭证；报表取数正确；ERP→MES→完工回传闭环 |

26 周（约 6 个月）含 2 周缓冲。

### M1 实际交付与验收偏差

M1 交付了 10 张 `md_*` 表、5 个 REST 资源（物料 / 客户供应商 / BOM / 工艺路线 / 工作中心）与对应前端页面。**验收标准里有三项与最初的写法不同**，如实记录：

| 原验收标准 | 实际做法 | 原因 |
|---|---|---|
| 物料 CSV 导入导出 | **未做**，改为「快速新建 + 选项式下拉 + 服务端搜索」 | CSV 导入的真正难点不是解析，是**错误报告**（第 37 行第 4 列的单位不存在，要能告诉用户）。草率做一个「导入失败」的弹窗比没有更糟。等 M2 有了库存初始化的真实导入需求，一起做带行级错误回显的导入向导 |
| BOM 多级展开用**递归 CTE** | 改为**应用层展开**（`BomExplosion`） | 展开要带损耗率放大、`base_qty` 折算、`maxLevels` 截断与环路标记；M4 的 MRP 还要复用同一份逻辑，只换数据来源。放 SQL 里等于把这段逻辑写两遍。详见 [domain/erd.md](domain/erd.md#bom-展开在哪算) |
| 与 MES `md_item` 可映射 | **字段级已具备映射条件，未写对接代码** | `code` / `name` / `spec` / `uom_code` / `item_type` 都是 MES `md_item` 的同名字段。真正的对接属于 M5 的集成里程碑，M1 阶段先把 `code` 唯一性与大小写归一化做扎实（MES 那边也是靠 code 认物料的） |

额外补的三条不变量（不在原计划里，但漏了会出事）：

1. **一个物料最多一个 `RELEASED` BOM**——否则 MRP 不知道该展开哪个版本
2. **被已发布 BOM 引用的物料（无论作为组件还是替代料）不能停用**——停用后 BOM 展开会拿到一个"不存在"的物料
3. **替代料不能指向自身，也不能指向该 BOM 的父物料**——后者是环路，展开时会无限递归

### M2 实际交付与验收偏差

M2 交付了 8 张 `inv_*` 表、6 个 REST 资源（仓库 / 库位 / 批次 / 库存 / 单据 / 流水）与对应前端页面。**验收标准里的四项与最初的写法不同**，如实记录：

| 原验收标准 | 实际做法 | 原因 |
|---|---|---|
| 出入库**单据**闭环 | 做了，但**单据只追加不修改**：`DRAFT → POSTED → REVERSED`，冲销用红字单据 | 原计划隐含"单据可以改"。库存单据不能改：过账后它已经产生了流水，改它就意味着账实不符。冲销不是改原单，而是**在原单旁边放一张红字单**，原单留在账上——审计要看到的是"错的那张"和"改的那张"，不是一个被抹平的空档 |
| 库存账实时 | 做了：**余额表与流水在同一事务里改** | "实时"如果靠定时任务刷新，盘点的人读到的就是几分钟前的世界。余额与流水同事务写入，两者永远不会不一致 |
| 批次追溯可查 | 做了：按批次可查全部流水与当前结存 | 批次与序列号**合并成一张 `inv_lot` 表**，用 `lot_type` 区分。序列号就是"只有一件的批次"——库存键、流水、追溯查询对两者是同一套逻辑，只有一个地方要查 |
| FIFO / 移动加权平均 | 只做**移动加权平均**，FIFO 未做 | 原计划把两者并列，实际二者互斥。移动加权平均的规则是"总额权威、均价推导"，总额只做加减因而精确累积；若以均价为准，每笔入库都要拿四舍五入过的均价乘数量，误差会在几千笔流水里滚雪球。FIFO 需要逐批次成本，归企业版 |

额外补的三条不变量（不在原计划里，但漏了会出事）：

1. **不能发出超过可用量的库存**——负库存不是小错误，它意味着账与架已经不一致，之后每一次计算都在继承这个谎
2. **有库存的物料不能停用**——这条规则横跨模块：主数据不能依赖库存模块，所以规则定义在 platform 的 `ItemUsageGuard` 接口上，由库存模块实现，主数据调用所有已注册的实现
3. **有库存的仓库不能停用**——否则余额指向一个谁也不能收发的地方

**未做**（留给 M3 及以后，如实记录）：`reserved` / `locked` 两个数量列已在表里，但 M2 恒为 0 —— 它们分别由销售单占用（M3）与质检/生产占用（M4）写入。列先留着，因为一张装着活数据的余额表临时加列是要迁移的。

## 5. 技术决策摘要

| 决策 | 选择 | 理由 | 详见 |
|---|---|---|---|
| 架构形态 | 模块化单体 | 中小厂部署简单、事务一致；高负载模块可后抽 | ADR-0001 |
| 多租户 | 共享 schema + `tenant_id` 行级隔离 | 运维简单、成本低、一套代码两种形态 | ADR-0002 |
| 模块化 | Maven 多模块 | Open Core 需要增值模块独立编译与授权 | ADR-0004 |
| 跨模块约束 | platform SPI 接口，模块各自实现 | 保持依赖单向，同时让"有库存不能停用"这类规则可插拔 | ADR-0005 |
| ORM | Spring Data JPA | 领域建模自然；复杂报表走原生 SQL | ADR-0001 |
| 认证 | 无状态 JWT（15 分钟 access / 7 天 refresh） | 便于水平扩展；租户与权限随 token 传递 | ADR-0003 |
| 数据库 | PostgreSQL 17 | 递归 CTE 做 BOM/MRP/追溯；JSONB 存审计快照 | ADR-0001 |
| 前端 | React 19 + Vite + TanStack Query + Zustand | 与 MES 对齐，统一品牌与工程范式 | — |

## 6. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 与 jshERP / T3rik 同质化 | MRP 进 MVP；ERP + MES 套件叙事；本土财税作为企业版抓手 |
| MRP 算法复杂度 | 先做净需求基础算法（毛需求 − 可用 − 在途 + 预留）；APS 放企业版 |
| 多租户隔离漏洞 | Hibernate `@TenantId` 框架级注入 + ArchUnit 守护 + 单租户部署兜底 |
| ERP/MES 边界模糊 | 见 docs/integration-mes.md 的职责表；MVP 只做单向集成 |
| 制造业需求碎片化 | 「不做清单」+ 企业版承载长尾 |
| Open Core 国内接受度 | Apache-2.0 降低采用门槛；先建社区与案例，再谈付费 |
| 长期维护投入 | 与 MES 共享设计系统 / 部署脚本 / ADR 范式 |
