# Genisource ERP 项目规划

> 版本：v0.1 | 日期：2026-10-27
> 状态：所有关键决策已确认，M0 已实施

---

## 0. 一页纸摘要

| 维度 | 结论 |
|---|---|
| 一句话定位 | 面向国内中小制造业的开源 ERP，以 MRP 运算为内核，与 Genisource MES 组成「计划层 + 执行层」套件。 |
| 目标客户 | 50–500 人、离散制造（电子装配、机加工、注塑、五金、小家电），1–3 个工厂。 |
| 核心价值 | BOM 算得准、MRP 算得快、采购销售库存财务一本账，并能与车间执行打通。 |
| 开源许可 | **Apache-2.0**，与 MES 统一；商业化走 Open Core（增值模块 + 服务）。 |
| 技术栈 | Java 21 + Spring Boot 4.1 + Spring Data JPA + Flyway + PostgreSQL 17；React 19 + TypeScript + Vite + TanStack Query + Zustand。 |
| 部署形态 | 多租户架构（行级隔离），一套代码同时支持私有化单租户与 SaaS 多租户。 |
| 与 MES 关系 | 独立仓库、独立部署，通过 REST API 集成。 |
| 最大风险 | 范围蔓延。必须靠「不做清单」和纵向切片保命。 |

## 2. 明确不做（写进 README，挡住需求）

- ❌ 全行业通用 ERP——只做离散制造，流程行业不在范围内
- ❌ 完整 APS 有限产能排程——核心只做 MRP 净需求，APS 属企业版
- ❌ WMS 立库调度、AGV 调度——只做仓库级库存
- ❌ 集团级合并报表、多会计准则——核心只做单组织简化财务
- ❌ 低代码表单引擎、可视化流程设计器——审批用 Flowable 内置 BPMN
- ❌ 自研数据库、消息中间件、工作流引擎
- ❌ 移动端 App（M5 之后评估，先用响应式 Web）

## 3. Open Core 边界

### 开源核心（Apache-2.0，永久免费）

平台基座（多租户 / RBAC / 审计 / 工作流 / 报表）、主数据（物料 / 客户 / 供应商 / BOM / 工艺 / 工作中心）、库存、采购到付款、销售到收款、MRP 运算、生产订单（计划层）、简化财务（凭证 / 总账 / 三大报表）、MES 集成适配器。

### 企业版增值（商业许可，`backend/ent-*`）

成本核算、APS 高级排产、QMS 质量管理、EAM 设备资产、多组织合并、高级财务（多币种 / 金税 / 预算）、移动端 PDA、BI 驾驶舱、SLA 支持。

**加载机制**：增值模块是独立 Maven 模块，通过 Spring Boot auto-configuration + `@ConditionalOnProperty` 按 License 加载；核心模块**禁止**依赖 `ent-*`，由 ArchUnit 守护（见 ADR-0004）。

### M1 实际交付与验收偏差

M1 交付了 10 张 `md_*` 表、5 个 REST 资源（物料 / 客户供应商 / BOM / 工艺路线 / 工作中心）与对应前端页面。**验收标准里有三项与最初的写法不同**，如实记录：

| 原验收标准 | 实际做法 | 原因 |
|---|---|---|
| 物料 CSV 导入导出 | **未做**，改为「快速新建 + 选项式下拉 + 服务端搜索」 | CSV 导入的真正难点不是解析，是**错误报告**（第 37 行第 4 列的单位不存在，要能告诉用户）。草率做一个「导入失败」的弹窗比没有更糟。等 M2 有了库存初始化的真实导入需求，一起做带行级错误回显的导入向导 |
| BOM 多级展开用**递归 CTE** | 改为**应用层展开**（`BomExplosion`） | 展开要带损耗率放大、`base_qty` 折算、`maxLevels` 截断与环路标记；M4 的 MRP 还要复用同一份逻辑，只换数据来源。放 SQL 里等于把这段逻辑写两遍。详见 [domain/erd.md](domain/erd.md#bom-展开在哪算) |
| 与 MES `md_item` 可映射 | **字段级已具备映射条件，未写对接代码** | `code` / `name` / `spec` / `uom_code` / `item_type` 都是 MES `md_item` 的同名字段。真正的对接属于 M5 的集成里程碑，M1 阶段先把 `code` 唯一性与大小写归一化做扎实（MES 那边也是靠 code 认物料的） |

额外补的三条不变量（不在原计划里，但漏了会出事）：

1. **一个物料最多一个 `RELEASED` BOM**——否则 MRP 不知道该展开哪个版本
2. **被已发布 BOM 引用的物料（无论作为组件还是替代料）不能停用**——停用后 BOM 展开会拿到一个"不存在"的物料
3. **替代料不能指向自身，也不能指向该 BOM 的父物料**——后者是环路，展开时会无限递归

### M2 实际交付与验收偏差

M2 交付了 8 张 `inv_*` 表、6 个 REST 资源（仓库 / 库位 / 批次 / 库存 / 单据 / 流水）与对应前端页面。**验收标准里的四项与最初的写法不同**，如实记录：

| 原验收标准 | 实际做法 | 原因 |
|---|---|---|
| 出入库**单据**闭环 | 做了，但**单据只追加不修改**：`DRAFT → POSTED → REVERSED`，冲销用红字单据 | 原计划隐含"单据可以改"。库存单据不能改：过账后它已经产生了流水，改它就意味着账实不符。冲销不是改原单，而是**在原单旁边放一张红字单**，原单留在账上——审计要看到的是"错的那张"和"改的那张"，不是一个被抹平的空档 |
| 库存账实时 | 做了：**余额表与流水在同一事务里改** | "实时"如果靠定时任务刷新，盘点的人读到的就是几分钟前的世界。余额与流水同事务写入，两者永远不会不一致 |
| 批次追溯可查 | 做了：按批次可查全部流水与当前结存 | 批次与序列号**合并成一张 `inv_lot` 表**，用 `lot_type` 区分。序列号就是"只有一件的批次"——库存键、流水、追溯查询对两者是同一套逻辑，只有一个地方要查 |
| FIFO / 移动加权平均 | 只做**移动加权平均**，FIFO 未做 | 原计划把两者并列，实际二者互斥。移动加权平均的规则是"总额权威、均价推导"，总额只做加减因而精确累积；若以均价为准，每笔入库都要拿四舍五入过的均价乘数量，误差会在几千笔流水里滚雪球。FIFO 需要逐批次成本，归企业版 |

额外补的三条不变量（不在原计划里，但漏了会出事）：

1. **不能发出超过可用量的库存**——负库存不是小错误，它意味着账与架已经不一致，之后每一次计算都在继承这个谎
2. **有库存的物料不能停用**——这条规则横跨模块：主数据不能依赖库存模块，所以规则定义在 platform 的 `ItemUsageGuard` 接口上，由库存模块实现，主数据调用所有已注册的实现
3. **有库存的仓库不能停用**——否则余额指向一个谁也不能收发的地方

**未做**（留给 M3 及以后，如实记录）：`reserved` / `locked` 两个数量列已在表里，但 M2 恒为 0 —— 它们分别由销售单占用（M3）与质检/生产占用（M4）写入。列先留着，因为一张装着活数据的余额表临时加列是要迁移的。

### M3 实际交付与验收偏差

M3 交付了 3 个 Maven 模块（`purchase` / `sales` / `finance`）、6 张业务表（`pur_document` + `pur_document_line`、`sal_document` + `sal_document_line` + `sal_reservation`、`fin_payable` / `fin_receivable`）、8 个 REST 资源与 8 个前端页面。**验收标准里的四项与最初的写法不同**，如实记录：

| 原验收标准 | 实际做法 | 原因 |
|---|---|---|
| Flowable 审批 | **未引入**，改为「金额阈值审批」：提交时低于 `erp.purchase.approval-threshold`（默认 5000）自动通过并留痕，高于阈值进入 `SUBMITTED` 等人批 | 计划把审批写成"接 Flowable"。一条采购单的审批只是"过 / 不过 + 一句意见"，为一个状态字段引入流程引擎、BPMN 模型与一张运行时表，成本远高于收益。真正的多级会签、加签、条件分支放到 M5 与财务凭证一起评估；到那时才会知道需要哪种引擎能力 |
| 收料**质检** | 未做，只做数量收料 | 质检是 QMS 的范畴（检验项、抽样方案、不良品处理、让步接收），计划里把它塞进收料这一步是把它说小了。收料单的 `location_id` / `lot_id` 已就位，质检放行后写入库位即可衔接 |
| 自动生成应收应付**凭证** | 生成的是**应收应付台账行**，不是会计凭证 | 凭证需要科目体系与借贷规则，那是 M5 的总账。M3 先落地"欠多少、什么时候到期、还了多少"，这部分不依赖科目也能算准，且是 M5 生成凭证时的唯一数据来源 |
| 端到端单据流转 | 做了，但**每张单据只追加**：`DRAFT → SUBMITTED → APPROVED → PARTIAL/COMPLETED → CLOSED`，出错走红字冲销 | 与 M2 一致。改一张已经执行过的订单，等于让"还剩多少没交"这个数字凭空变化 |

M2 留下的 `reserved` 列已由销售订单确认时写入：订单确认按「满箱优先」挑余额行，`sal_reservation` 记下**哪一行余额承诺给了哪一行订单**，发货过账时先释放承诺再出库。`locked` 仍恒为 0，留给 M4（质检 / 生产占用）。

额外补的四条不变量（不在原计划里，但漏了会出事）：

1. **同一笔业务只能生成一张应收/应付**——`UNIQUE (tenant_id, source_type, source_id)`。重复过账、双击提交、网络重试都不允许把一笔账记两遍
2. **税额不进库存成本**——收料按**不含税价**过账。把进项税摊进移动加权平均，之后每一次出库都会继承一个虚高的单价
3. **占用先释放、再出库**——出库校验的是"可用量"，而还承诺给本订单的库存不算可用。顺序反了就会自己拒绝自己
4. **状态由金额推导，不单独存**——应收/应付的 `status = of(total, paid)`，`amount_paid` 是唯一事实来源。存两份状态就会有"显示已结清但余额不为零"的一天

**未做**（留给 M4 及以后，如实记录）：多级审批与会签、收料质检、价格表与折扣、销售退货、采购退换、多币种、`locked` 占用、由业务单据生成会计凭证。

### M4 实际交付与验收偏差

M4 交付了 2 个 Maven 模块（`production` / `mrp`）、6 张表（`prd_production_order` + `prd_order_line` + `prd_order_operation`、`mrp_run` + `mrp_demand` + `mrp_plan_supply`）、2 个 REST 资源（`/api/production/orders`、`/api/mrp/runs`）与 2 个前端页面。**验收标准里的五处与最初的写法不同**，如实记录：

| 原验收标准 | 实际做法 | 原因 |
|---|---|---|
| MRP 净需求「毛需求 − 可用 − 在途 + 预留」 | 公式改为**毛需求 + 安全库存 + 窗口外预留 − 现存 − 已锁定 − 在途**，且**逐层结算**而非一次性递归展开 | 原式子里的「+ 预留」会重复计数：窗口**内**订单已经预留的货仍在仓库（计入现存），订单本身也在毛需求里，加回去等于把这批货数两遍。展开则必须逐层做——每层先把需求与库存结清，再问「它由什么构成」，同一物料被多条路径触达时只记在**最浅**那层 |
| 计划工单 / 计划采购单 | **没有独立的「计划单」表**。`mrp_plan_supply` 是**建议行**，三态 `PLANNED → CONVERTED / IGNORED`；转单时直接调 `PurchaseService.create` / `ProductionService.create` 生成真实单据，回写 `converted_type` / `converted_no` | 若先做「计划单」再转「执行单」，就是两套单据、两次状态流转、两个单号序列，而且「计划单已转」和「执行单已下」迟早会不一致。建议行的生命周期只有三态，转完就结束 |
| 生产订单可下达 MES | **未做**。下达（release）的含义是「锁定物料 + 变为可领料」，不推送 MES；`mes_wo_no` 字段已就位 | MES 侧接口与**完工回传**契约要一起设计（见 [integration-mes.md](integration-mes.md)），先做单向推送等于要改两次。M5 与完工回传一起做 |
| 领料、完工入库 | 做了，但**不另立单据体系**：领料 = `OUTBOUND`、完工 = `INBOUND`，`source_type = PRD_ORDER`，走 M2 已验证的过账 / 冲销 / 移动加权平均 | 库存只有一个入口才只有一个账。生产模块自建一套「领料单」会让同一批钢材有两个说法，盘点时对不上就再也说不清是谁写错了 |
| 生产订单沿用 `DocumentLifecycle` | 另立 `ProductionOrderStatus`：`PLANNED → RELEASED → IN_PROGRESS → COMPLETED`，旁支 `CLOSED` / `CANCELLED` | 「已下达」既不是审批通过也不是已发货。硬套会让单据状态机里长出一堆只对生产有意义的状态，而采购/销售那边永远也用不到 |

M2 留下的 `locked` 列已由生产订单下达时写入：按「满箱优先」从 `inv_stock` 里锁，`prd_order_line.qty_locked` 记录锁了多少；领料时**先释放锁定再出库**。至此 `reserved`（M3 销售）与 `locked`（M4 生产）两列都有了真实的写入方。

额外补的五条不变量（不在原计划里，但漏了会出事）：

1. **同一物料一次运算只出一条建议，到期日取最早**——否则同一个钢材会出现「缺 2、缺 5」两行，计划员得自己加；加错了就是重复下单
2. **领料必须先释放本单的锁定、再出库**——顺序反了，出库校验的可用量里还含着本单自己的锁定，会自己拒绝自己
3. **缺料允许下达，但未指定仓库不能下达**——缺料是常态，卡住下达等于让计划层无法表达真实存在的缺口；而仓库不知道，就不知道该去哪锁料
4. **工序是复制，不是引用工艺路线**——工艺路线日后改版本，已下达的工单不受影响。车间拿到的是下单那一刻的工艺，这符合「下达即冻结」的语义
5. **完工入库按物料标准成本计价**——生产订单还没有成本归集（M5 才有），标准成本是当前唯一不撒谎的价；实际与标准的差异留给 M5 做成本差异分析，不在完工时编一个价

**未做**（留给 M5 及以后，如实记录）：MES 下达与完工回传、产能校验与 APS 排产、工序报工（只有 `PENDING` / `DONE`，不记实际工时）、替代料参与 MRP 展开、按订单归集成本、同一物料不同交期的分行建议（现在合并成一条取最早到期日）、FIFO 计价。

验收用的真实数字（`/tmp/m4_e2e.py`，99 项断言全绿）：销售单 5 件、成品现存 5、安全库存 2 → 净需求 2；两级 BOM 展开出半成品 2、钢材 10（成品直用 4 + 半成品带出 6）；钢材最小起订量 100 → 建议 100 公斤、提前期 5 天推算出下单日；下达锁定 6 公斤，领料后库存 100 → 94、锁定归零；完工 2 件按标准成本 15 入库。随后那张 100 公斤的采购单让钢材净需求变成 −90，**自动从建议里消失**——这是「在途抵扣」真正生效的证据。


### M5 实际交付与验收偏差

M5 交付了 1 个新模块（`integration`）、6 张表（`fin_account` / `fin_voucher` / `fin_voucher_line` / `fin_settlement` / `int_mes_outbox` / `int_mes_completion`）、6 个 REST 资源（科目表、凭证、总账与三大报表、MES 出入站）与 4 个前端页面（科目表、凭证、报表、MES 集成）。**验收标准里的六处与最初的写法不同**，如实记录：

| 原验收标准 | 实际做法 | 原因 |
|---|---|---|
| 业务单据自动生成**凭证** | 做了，但**自动凭证与手工凭证是两扇门**：收料、发货、领料、完工、付款、收款在**同一事务**里写下自己的凭证（出生即已过账）；手工凭证先进 `DRAFT`，另一个人点过账才进账簿 | 库存动了而总账没动，就成了两本账。自动凭证如果也要等人过账，收料单就会躺在「已过账但没记账」的状态里，那才是真的两本账 |
| 凭证冲销 | **红字冲销**：原凭证变成 `REVERSED` 并**继续计入**账簿，旁边的红字凭证（借贷对调）也计入，两者相抵 | 「把原凭证排除、只留红字」是错的——红字的借贷是对调的，只算红字等于把发生过的事**反过来**记了一遍。规则因此只有一句：**除草稿外都算** |
| 三大报表 | 做了，但**现金流量表是直接法**，按现金科目的对方科目分类（收入/成本/费用→经营，资产→投资，负债/权益→筹资），分类不出来的进「其他」 | 法定现金流量表是间接法，从净利润倒推。这份是从凭证正向汇总的**直接法**，口径与准则报表对不上，文档里写明，不假装是准则报表 |
| MES 双向集成 | 做了 ERP→MES 下达与 MES→ERP 完工回传、进度回传；**物料同步（3.4）与重试队列的「4 次后告警」未做** | 重试队列本身做了（退避 1m→5m→30m→2h，超过次数标记 `DEAD`），但「告警」需要企业版的告警通道，开源版没有可接的地方 |
| 硬化 | 做了能做的：5xx 现在会记日志、ArchUnit 守卫加了 2 条（集成模块在依赖图边缘、生产不依赖财务）、新增 2 个表前缀 `fin_` / `int_`、离线包脚本 | 「硬化」在计划里是一个筐，真正的性能压测与故障演练没做 |
| 离线包 | 做了 `deploy/scripts/offline-package.sh`：导出镜像 tar + compose + 安装脚本 + 一页 INSTALL 说明 | 一台没有外网的机器上，ERP 装不上就什么都不是 |

**M3 留下的台账终于接上了凭证**：M3 只做应收应付台账（欠多少、什么时候到期、还了多少），M5 才把它变成会计语言——收料借原材料与进项税、贷应付账款；发货借应收账款、贷收入与销项税，同时按库存流水的实际金额结转销售成本；领料借生产成本、贷原材料；完工借库存商品、贷生产成本。

**成本归集只到材料层**：完工入库按物料标准成本计价（沿用 M4 的决定），而领料按库存流水的移动加权平均成本入生产成本。两者之差（标准成本里含的人工与制造费用）留在生产成本科目的贷方——**这不是算错了，是成本核算模块（企业版）还没有归集人工与费用**。资产负债表仍然平衡：差额挂在在产品上，等企业版成本模块接管。

额外补的六条不变量（不在原计划里，但漏了会出事）：

1. **一张来源单据只写一张凭证**——`UNIQUE (tenant_id, source_type, source_id)`，`source_id` 可空时用 `COALESCE(source_id, 0)` 折叠，手工凭证的 `source_id` 为空因此不受约束
2. **凭证必须借贷相等才能过账**，不平的差额会直接写进错误信息
3. **只能记到明细科目**：汇总科目（有下级的）和已停用的科目都拒绝记账
4. **科目代码与类别一旦被凭证引用就冻结**——改代码会静默地给所有历史报表换标签
5. **自动凭证的规则不写死科目代码，只写「角色」**（`INVENTORY_RAW` / `AP` / `TAX_INPUT`…）——工厂把 `1403` 改成 `140301` 是数据改动，不是代码改动
6. **MES 完工回传按 `mesCompletionId` 幂等**——MES 重试、网络重试都不能把同一批成品入账两次

**未做**（留给企业版或 M5 之后，如实记录）：成本核算（人工、制造费用、差异分摊）、期末结转损益与利润分配、现金流量表的间接法、现金流量表附注、资产负债表附注、MES 物料同步（3.4）、多币种与金税、集团合并。

**v1.0 交付形态（离线包）**：`deploy/scripts/offline-package.sh` 把两个镜像导出成 tar，连同 compose、脚本与一页 INSTALL 说明打成一个目录。目标机器**不需要源码、不需要外网**，只要有 Docker：`docker load` 之后运行 `scripts/install.sh` 即可。安装脚本同时认两种布局——仓库里（从源码构建）与离线包里（载入镜像），靠「旁边有没有 compose.yaml 和 images/」判断，不靠参数。

这一轮把离线包**真装了一遍**（192MB 的包，4 个容器全部 healthy，登录与各模块接口均正常），并因此发现两处从未跑通过的问题，如实记录：

| 问题 | 原因 | 处理 |
|---|---|---|
| **容器镜像从 M1 起就构建不出来** | `backend.Dockerfile` 只复制了 `platform` 与 `bootstrap` 两个模块，而父 POM 已经把八个模块列为子模块——Maven 读不到 reactor 直接失败 | Dockerfile 补齐全部九个模块的 POM 与源码；POM 先复制、源码后复制，改一个 Java 文件不必重新下载依赖 |
| **未知路径返回 500** | Spring 把「没有这个路由」报成 `NoResourceFoundException`，被兜底分支当成服务器故障，记了整页堆栈 | 加了专门的处理器，答案是 404——调用方要的东西不存在，不是我们的错 |

验收用的真实数字（`/tmp/m5_e2e.py`，106 项断言全绿；`/tmp/m5_mes_e2e.py`，23 项断言全绿）：买 100 公斤钢材付 565（含税 65）→ 借原材料 500、进项税 65、贷应付 565；两级生产（半成品 2 件 → 成品 2 件）→ 领料按实际成本贷原材料、完工按标准成本借库存商品；发货 2 件 → 借应收账款 226、贷收入 200 与销项税 26，同时结转销售成本 160；收料 200 + 365 两笔付款后应付归零，收款 226 后应收归零。**试算平衡表期末借贷相等，资产负债表差额为 0**，利润 40。

## 5. 技术决策摘要

| 决策 | 选择 | 理由 | 详见 |
|---|---|---|---|
| 架构形态 | 模块化单体 | 中小厂部署简单、事务一致；高负载模块可后抽 | ADR-0001 |
| 多租户 | 共享 schema + `tenant_id` 行级隔离 | 运维简单、成本低、一套代码两种形态 | ADR-0002 |
| 模块化 | Maven 多模块 | Open Core 需要增值模块独立编译与授权 | ADR-0004 |
| 跨模块约束 | platform SPI 接口，模块各自实现 | 保持依赖单向，同时让"有库存不能停用"这类规则可插拔 | ADR-0005 |
| ORM | Spring Data JPA | 领域建模自然；复杂报表走原生 SQL | ADR-0001 |
| 认证 | 无状态 JWT（15 分钟 access / 7 天 refresh） | 便于水平扩展；租户与权限随 token 传递 | ADR-0003 |
| 数据库 | PostgreSQL 17 | 递归 CTE 做 BOM/MRP/追溯；JSONB 存审计快照 | ADR-0001 |
| 前端 | React 19 + Vite + TanStack Query + Zustand | 与 MES 对齐，统一品牌与工程范式 | — |
| 单据编号 | `sys_doc_counter` + `INSERT … ON CONFLICT DO UPDATE … RETURNING` | 「数一数再加一」在并发下会出重号；取号只能是一次原子的自增，不能是先读后写 | — |
| 单据状态 | 一个 `DocumentLifecycle` 枚举，审批只留痕不另设状态 | 「已审批」且「已发一半」是同时成立的，两个字段就得手工保持同步 | — |

## 6. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 与 jshERP / T3rik 同质化 | MRP 进 MVP；ERP + MES 套件叙事；本土财税作为企业版抓手 |
| MRP 算法复杂度 | 先做净需求基础算法（毛需求 − 可用 − 在途 + 预留）；APS 放企业版 |
| 多租户隔离漏洞 | Hibernate `@TenantId` 框架级注入 + ArchUnit 守护 + 单租户部署兜底 |
| ERP/MES 边界模糊 | 见 docs/integration-mes.md 的职责表；MVP 只做单向集成 |
| 制造业需求碎片化 | 「不做清单」+ 企业版承载长尾 |
| Open Core 国内接受度 | Apache-2.0 降低采用门槛；先建社区与案例，再谈付费 |
| 长期维护投入 | 与 MES 共享设计系统 / 部署脚本 / ADR 范式 |
