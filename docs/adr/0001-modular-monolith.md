# ADR-0001：采用模块化单体而非微服务

- 状态：Accepted
- 日期：2026-10-27

## 背景

目标客户是 50–500 人的离散制造工厂，典型部署是一台 4C8G 的内网服务器，IT 支持往往只有一个人（甚至由厂长兼任）。ERP 的业务特征恰恰是**跨模块强一致**：一张销售发货单要同时扣减库存、生成应收凭证、更新订单执行状态；一次 MRP 运算要读 BOM、库存、在途、销售订单，写出计划工单与计划采购单。

同时，项目由 1–2 人推进，需要在一到两年内持续交付 M1–M5。

## 决策

采用**模块化单体**：单个 Spring Boot 应用、单个数据库、单个部署单元，但代码按业务模块严格分区（Maven 多模块 + 包边界），模块间通过应用服务接口与领域事件协作，禁止跨模块直接访问 Repository。

与 Genisource MES 保持一致（MES ADR-0001 已做同样论证），便于共享工程范式。

## 后果

**收益**

- 跨模块事务天然一致，不需要 Saga、最终一致性补偿、分布式锁
- 部署与运维只有一组容器，安装脚本、备份脚本、升级脚本都能保持简单
- 本地开发一条命令即可跑全栈，降低外部贡献者的门槛
- 模块边界靠 ArchUnit 强制（`backend/platform/src/test/.../ModuleBoundaryTest`），随规模增长仍可维护

**代价**

- 无法按模块独立扩容。MRP 运算与月末结账是仅有的两个 CPU 尖峰，届时可把 `mrp` 模块抽成独立进程，通过领域事件异步触发，不需要整体重构
- 单进程故障影响全部功能。对单厂私有化场景这是可接受的（本来就只有一台服务器）

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 微服务 | 中小厂没有 K8s 运维能力；跨服务事务会把最简单的「发货单」变成分布式事务问题；团队规模撑不起服务治理 |
| 单体但单模块（不做模块分区） | 6 个月后必然出现「谁都能改任何表」，Open Core 的增值模块也无法独立授权 |
| 模块化单体 + 独立数据库 per module | 引入跨库事务，代价高于收益 |
