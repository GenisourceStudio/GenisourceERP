# ADR-0005：跨模块约束通过 platform SPI 表达

- 状态：Accepted
- 日期：2026-10-27
- 决策者：项目组

## 背景

M1 交付后出现第一条跨模块的约束：**被已发布 BOM 引用的物料不能停用**（组件和替代料两条引用路径都要查）。规则归主数据所有，检查却需要读 BOM——这没问题，两者同属 masterdata 模块。

M2 带来第二条：**有库存的物料不能停用**。这条规则归主数据所有，检查却需要读库存表。

于是主数据要么依赖库存模块，要么库存模块依赖主数据。两个方向都会破坏 ADR-0004 划定的依赖方向：

- 主数据 → 库存：主数据是依赖图的底座，它一旦开始消费下游模块，"主数据是最底层"这句话就不再成立；
- 库存 → 主数据：库存本来就需要物料，这条本来就有，问题在于主数据无法反向调用库存。

第二条其实是个**双向需求**：库存要知道物料，主数据也要知道库存。

## 决策

把跨模块的约束表达成**平台层的接口**，由"拥有约束的那一侧"实现：

```java
// platform/common/ItemUsageGuard.java
public interface ItemUsageGuard {
    void assertCanDeactivate(Long itemId);
}
```

主数据注入它找到的**所有**实现，逐个调用：

```java
for (ItemUsageGuard guard : usageGuards) {
    guard.assertCanDeactivate(id);
}
```

库存模块提供实现（`StockItemUsageGuard`），它只查自己的 `inv_stock` 表。

依赖方向因此始终是单向的：`inventory → masterdata → platform`。运行时主数据会调用库存提供的实现，但**编译期**不存在这个依赖——主数据只认 platform 里的接口。

## 理由

1. **依赖图保持单向**。ArchUnit 的四条规则继续成立，且不需要为每一条跨模块约束开一个特例。
2. **可选部署仍然可用**。装配了库存模块就有库存的约束；没装配就没有——物料可以被停用，这对一个不含库存的系统是正确的行为。
3. **扩展点符合 Open Core 的形态**。将来"客户余额不为零时不能停用""有未清订单时不能停用"都是同一个形状：各自模块实现同一个接口，主数据代码不动。这正是社区版与商业版共存的机制。
4. **主数据不需要知道下游的存在**。主数据代码里出现的只有 `ItemUsageGuard`，不是 `StockRepository`。

## 代价

1. **约束是运行时的，不是编译期的**。漏掉某个实现，主数据不会报错——它只是少了一道检查。缓解办法是把实现放在模块自己的包里，并给关键约束写集成测试。
2. **调用顺序不保证**。多个 `ItemUsageGuard` 的调用次序取决于 Spring 的注入顺序；这不影响正确性（各守卫互不依赖），但错误信息里守卫的先后顺序不固定。
3. **接口放在 platform 会让 platform 逐渐变成"杂物间"**。判据是：只有当一个约束**被多个模块以同一种方式需要**时，它才配得上进 platform。一次性约束应当留在模块内部。
